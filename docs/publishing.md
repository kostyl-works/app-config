# Публикация prod и dev

Оба окружения находятся в одной ветке `main`, имеют отдельные файлы, версии и теги.
Разработчик приложения выбирает шаблон ссылки по флейвору.

| Окружение | Редактируемый файл | Собранный файл | Тег |
| --- | --- | --- | --- |
| prod | `hosts.json` | `config.json` | `1.0.N` |
| dev | `dev/hosts.json` | `dev/config.json` | `dev-1.0.N` |

В `hosts.json` указывается `endpoints_enabled` и массивы HTTPS-origin для ролей
`api`, `superapi`, `web`, `oauth`, `cdn`, `analytics`. Пути и параметры в хостах запрещены.
Адреса двух окружений первоначально оставлены как есть; имя prod не означает,
что в его файле уже стоят продовые серверы.

## Ссылки

`N` — поле `version` соответствующего конфига, без ведущих нулей:

```text
prod: https://cdn.jsdelivr.net/gh/kostyl-works/app-config@1.0.N/config.json
dev:  https://cdn.jsdelivr.net/gh/kostyl-works/app-config@dev-1.0.N/dev/config.json
```

У prod и dev независимая нумерация. Новая версия dev не меняет версию prod.
Теги после публикации не перемещаем: для изменения содержимого выпускаем новую версию.
Для dev используем точные теги, а не prod-диапазон `@1` или `@latest`.
URL через `@main` кешируется jsDelivr на 12 часов и не подходит для быстрой проверки обновлений.
Правила: https://github.com/jsdelivr/jsdelivr#caching

## Автоматический запуск

1. Измените `dev/hosts.json` для тестирования или корневой `hosts.json` для prod.
2. Закоммитьте изменение в `main` напрямую или через PR.
3. Workflow **Publish hosts** автоматически проверит новые хосты, соберёт JSON,
   увеличит версию только выбранного окружения, закоммитит его и создаст тег.
4. Откройте **Actions → нужный запуск → Summary**. Там будут окружение, версия,
   точная ссылка и строка JSON для `endpoints_config` в Varioqub соответствующего окружения.

Если в одном push изменены оба `hosts.json`, будут опубликованы оба окружения
последовательно. Ошибка одного не отменяет попытку опубликовать другое.
Проверяются изменения всего push, а не только последнего коммита.
Запуски используют общую очередь, потому что оба окружения коммитят в `main`.

Версию и собранные `config.json` вручную не правим. Если содержимое не изменилось,
новая версия не создаётся. При первом запуске тег создаётся и для уже собранного JSON;
это позволяет опубликовать начальный `dev/config.json` с version 1.
Первая публикация dev произойдёт после добавления `dev/hosts.json` в `main`.
До успешного запуска новый dev-адрес ещё не опубликован.

## Ручной запуск и повтор

1. **GitHub → Actions → Publish hosts → Run workflow**.
2. В поле ветки выберите **main**.
3. В `environment` выберите **dev** или **prod**. По умолчанию выбран dev.
4. Обычно оставьте `skip_check` выключенным. Включите его, если хост намеренно ещё
   не поднят или проверку DNS/TLS нужно пропустить. Проверка формата JSON останется.
5. Нажмите **Run workflow** и заберите ссылку из Summary.

Ручной запуск собирает актуальный `hosts.json` выбранного окружения из `main`.
Повтор уже опубликованной версии не создаёт коммит и не переписывает тег.
Если тег занят другим содержимым, публикация завершится ошибкой вместо его перезаписи.
Проверка с GitHub-раннера подтверждает DNS/TLS, но не доступность из сети тестировщика.

## Почему одна ветка

Отдельная ветка `development` здесь не нужна: окружение определяется путём файла.
Мердж dev-конфига в prod сам по себе не означает, что тестовые домены должны попасть
в релиз. Проверенные изменения переносим в корневой `hosts.json` отдельным изменением.

## Подпись и Rutube (SAM-809)

`config.json` — не плейнтекст, а **подписанный конверт**
`{"p": base64url(байты конфига), "s": base64url(подпись Ed25519)}`. Приложение проверяет
подпись ДО разбора и отвергает неподписанное (fail-closed). Внутри конфига поле `etag` —
зашифрованный список `videoId` каналов Rutube. Формат конверта один во всех каналах.

Тот же конверт разливается в **описания видео Rutube** (запасной канал при «белых списках»):
на каждое видео из `rutube.json` / `dev/rutube.json` конверт шифруется ключом с солью = `videoId`
и кладётся между метками `~(` … `)~` в описание. Метки — из символов, которые Rutube не меняет
(`<`/`>` он подменяет Unicode-двойниками) и которых нет в base64url.

### Файлы видео

`rutube.json` (prod) и `dev/rutube.json` (dev): `{"videos":[{"id":"<32 hex>","token":"<метка>"}]}`.
`id` — видео, `token` — метка аккаунта в секрете токенов своего окружения (`RUTUBE_TOKENS_PROD`
/ `RUTUBE_TOKENS_DEV`). Метка — нейтральное слово: файл и логи Actions публичные, почту или
логин учётки в метку не класть. Изменение этих файлов тоже запускает публикацию соответствующего
окружения.

### Секреты

| Секрет | Что это | Откуда |
| --- | --- | --- |
| `SIGN_KEY_PROD` / `SIGN_KEY_DEV` | приватный ключ подписи | `crypto/keys.sh` (репозиторий приложения) |
| `CIPHER_KEY_PROD` / `CIPHER_KEY_DEV` | ключ шифрования `etag` и описаний | там же |
| `RUTUBE_TOKENS_PROD` / `RUTUBE_TOKENS_DEV` | `{"<метка>":"<refresh-токен>"}` | мануал получения токена |
| `RUTUBE_TOKENS` | старый общий секрет dev | читается, только пока нет `RUTUBE_TOKENS_DEV`; после первого dev-прогона удалить |
| `GH_PAT` | PAT с правом `secrets:write` | нужен для записи нового refresh-токена |

Приватные ключи заводит `crypto/keys.sh → init` (репозиторий приложения). Мануал ключей:
`docs/features/dynamic-base-url/08_key_flow.md`. Мануал токена Rutube:
`docs/features/dynamic-base-url/rutube/05_refresh_token_manual.md`.

### Ротация токена Rutube

Refresh-токен **одноразовый**: при каждом обновлении access-токена Rutube отдаёт новый, старый
гаснет. CI сохраняет новый обратно в секрет своего окружения через `GH_PAT`. Секреты раздельные,
потому что секрет GitHub не читается: дописать метку в общий словарь нельзя, а запись целиком
перетёрла бы токены другого окружения. Токеном нельзя пользоваться нигде, кроме CI — ни для
проверок, ни для чего-либо ещё: любой обмен сжигает его. **Без `GH_PAT`** шаг
отработает один раз и предупредит, что следующий прогон упадёт — тогда токен обновляют вручную
по мануалу. Все ошибки шага Rutube пишут, что обновить и где мануал.

## Проверка скриптов

```sh
node --test
bash -n scripts/release.sh
```

Тесты работают во временных Git-репозиториях с локальным bare remote и не публикуют
ничего на GitHub или jsDelivr. Проверки release используют заглушку curl.
